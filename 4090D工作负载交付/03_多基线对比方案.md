# 多到达率下的基线对比方案

2026-11-05 更新。五方法入口及本地验证已完成，新增 GPU 实验尚未执行。

我们将在相同模型、输入和到达时间表下比较原生 vLLM、vLLM+LMCache、static TTL、Continuum 和 Kairos。主要考察程序平均完成时间，辅以 P95、吞吐、完成率和资源占用。相对原生的约 1.5 倍收益作为本项目的目标，最终以实际结果判断。

## 方法定义和入口状态

| 方法 | 本轮定义 | 当前本地交付的支持情况 |
|---|---|---|
| 原生 vLLM | 标准请求级调度，固定并记录 prefix caching 设置，计划开启；使用原生 GPU KV 管理 | 已增加标准启动配置与客户端入口；GPU 待验证 |
| vLLM+LMCache | 在同一 vLLM 基线上接入标准 LMCache CPU 缓存，保持请求级调度，CPU KV 上限 8 GiB | 已增加标准 connector 配置；GPU 待验证 |
| static TTL | 在 Continuum 路径上保留程序级调度，采用预先确定的固定 TTL。缓存层、回收与队列行为逐项记录 | 已增加独立策略类及实际阈值日志检查；采用常数工程对照，GPU 待验证 |

## 公平比较所固定的条件

- 采用 Qwen3-8B BF16、同一 snapshot 和 tokenizer、同一 vLLM 版本，同一 4090D 及容器限制。
- 固定 pilot_14 的 14 个程序、161 次调用、24,182 token 输出预算及原始工具反馈间隔。同一到达率的所有方法逐字节复用同一份到达表。
- 固定 16K 上下文、8 个生成槽位、批处理 token 上限和 GPU 内存预算，记录每个方法实际分配的 KV 块数。对有 CPU 缓存的方法固定 8 GiB 容量，并分别记录实际占用。
- 各方法从同等冷缓存状态开始，新流程统一使用刚启动的引擎，仅执行引擎初始化及图捕获，健康检查后直接回放，轮换执行顺序。保留 GPU 占用证据；共享干扰明显的结果单列。
- 原生与标准 LMCache 入口需要接受相同的整数 token 输入及固定输出预算，复用相同程序依赖与等待逻辑。方法专属字段按接口能力发送，所有方法统一核对实际 prompt 签名与输出 token 数。

## 约 1.5 倍的判断口径

组长尚未明确 1.5 倍指延迟还是吞吐。本方案暂以程序平均完成时间作为主指标，同时完整报告吞吐比值。Continuum 与 Kairos 分别计算相对原生的收益，避免合并两者。

```text
程序完成时间加速比 = 原生 vLLM 的平均 JCT / 对比方法的平均 JCT
输出吞吐比 = 对比方法的输出 token/s / 原生 vLLM 的输出 token/s
```

例如，原生平均 JCT 为 60 秒、对比方法为 40 秒，则完成时间加速比为 1.5 倍，耗时降低约 33.3%。每个方法先逐轮求 14 个程序的平均 JCT，再报告重复轮次的均值和范围；相对收益用同档重复轮次均值计算。P95 和失败情况同时展示。

报告呈现全部到达率的结果。约 1.5 倍是本项目的目标值；达到与未达到的档位均保留。现有单次 Kairos 记录缺少同条件原生测量，当前加速比为“待测”。固定输出量下的批次吞吐还受输入到达和排空影响，应连同观察窗解释。

## 实现与剩余验收

五方法统一入口为 b_replay.comparison，统一汇总为 b_replay.comparison_results。三档五方法配置检查、完整模拟回放、失败保留、固定 TTL 策略重置回归和结果核验已完成。新流程采用一致的进程冷启动条件，与旧先导的客户端预热流程存在差异，因此旧实测单列。

当前 static_ttl 是“固定常数 + Continuum 程序级调度”的工程消融，必须显式指定 TTL。论文冷启动估计值的推导与实现仍是可选的后续扩展。正式结果注明使用的定义与常数。
