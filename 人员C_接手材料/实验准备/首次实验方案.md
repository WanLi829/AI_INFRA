## 3. 归档负载实际有多大

本地读取固定提交的原始文件并重建逐轮输入，结果保存在 [归档负载统计.json](归档负载统计.json)。分位数使用 nearest-rank；中位数使用普通样本中位数。

| 项目 | 统计结果 |
|---|---|
| 程序数 / 请求数 | 16 / 178 |
| 每程序轮数 | 最少 7，中位数 11.5，最多 15 |
| 单请求输入长度 | 最少 1,218，中位数 5,247.5，P95 为 8,727，最多 11,455 tokens |
| 单请求计划输出长度 | 最少 39，中位数 104，最多 699 tokens |
| 全部请求计划输出总量 | 26,164 tokens |
| 非末轮的工具等待 | 中位数约 0.276 秒，P95 约 2.977 秒，最大约 6.477 秒 |
| 程序到达时间 | 相对回放开始 0.263108～2.909618 秒；本数据没有 predecessor 依赖 |
| 非首轮输入中的显式保留前缀比例 | 按 token 总量加权约 88.74% |

前缀比例定义为非首轮 `keep_prefix_tokens` 总和除以非首轮完整输入 token 总和。它只是输入结构，不是实际缓存命中率。所有程序在约 3 秒内到达，也不等于 GPU 始终同时处理 16 个请求。

检查了 372 个本地条件：逐程序消息轮数对应、前缀长度合法、重建输入长度与声明一致，全部通过。没有重新运行 tokenizer，也未测量模型速度、显存或缓存命中。

2026-11-02 补充核对：回放器通用的“合成 token 身份”标签不能直接用于判断此归档的来源。固定版本 EXPERIMENTS 与 THIRD_PARTY 说明该负载保留 SWE teacher 内容，改写首次到达与首个工具等待；历史 tokenizer 记录显示 178 次输入在 8B 上核对一致。它是构造的 teacher replay 压力负载，不是自然生产到达或自主 Agent 成功率评测。详见 [现有负载分析报告](负载分析/现有负载分析报告.md)。

## 4. 上机之前要解决的资源差异

云平台已核查的实例为 `a3cffd6bfa05`，RTX 4090D 24GB、10 核 CPU、标注内存 30GB，系统盘和缓存盘各 50GB，页面单价 2 元/小时。平台入口为 [子用户登录](https://ai.bayesdl.com/base/login)，账号密码不写入实验材料。

实现小组的历史记录是 251GB RAM，而固定版本启动代码要求至少 40GiB 可用主机内存。平台标注的 30GB 与该条件有冲突，不能预设能够直接复跑。

1. 可先请实现小组说明历史运行是否用同一实例，是否存在容器额度与宿主机显示不一致的情况。
2. 下次连接后检查 `free -h`、容器 cgroup 的内存上限与当前用量、允许的 CPU 集合。只看 `free -h` 可能误把宿主机内存当作容器可用额度。
3. 若实际资源不满足原版要求，停止启动模型，将资源记录反馈给实现小组，确定适配版本或资源安排。不通过删除 40GiB 检查来宣称已解决。
4. 历史 CPU 编号 `4-5,68-69` / `6-7,70-71` 也须现场核查，不能从“10 核”推断具体可用编号。

已有 [服务器只读检查脚本](../服务器只读检查.sh) 可检查基础环境，但它尚未覆盖 cgroup 内存额度，也不等于完整模型权重验证。

| 5：新数据接入 | 实现小组提供正式接入方式后，测试杨智涵交付的最小完整数据包 | 数据与消息、tokenizer、协议及校验一致；完整执行通过 |
| 6：逐项扩展 | 一次只改一个负载因素；有候选配置后，两种方法各独立运行至少 3 次 | 保存每次原始结果与失败记录，具备可比较的重复样本 |

“一次最小复跑”在当前发布版中仍是完整归档 178 请求。单程序样例只能检查接口；当前 CLI 没有 `--trace`、`--workload`、任务数或并发数参数，不能凭空加入这些开关。

首次模型编译和预热可能较慢，REPRO 的启动等待上限为 2400 秒；上机时间及预算应覆盖准备和启动过程，不假定几十秒内完成。

## 6. 新负载与压力实验的拟定顺序

以下是准备方向，尚未配置为可直接运行的矩阵；需要正式接入支持。

1. **最小输入：** 一个完整多轮程序；保留前缀、工具等待与输出长度信息，验证数据接口。
2. **小批输入：** 建议先交付 2～4 个完整程序，覆盖短/较长上下文和短/较长工具等待。这是首批交付建议，不是已验证的 24GB 容量上限。
3. **压力扩展：** 固定模型和程序内容，只调整程序到达间隔或活跃程序数量；记录真实并发，保留工具等待规则。
4. **特征对照：** 选择不同前缀复用或工具等待特征的负载；调整等待时记录缩放比例和理由，不能直接混比不同输入。
5. **模型与缓存扩展：** 4B、CPU KV 容量调整由实现小组明确支持后另设实验组。不要把模型变化和负载压力变化混在同一个对照中。

适用性的判断同时包含：来源和场景有依据、数据可重放、资源可容纳、运行稳定、具有可观察的缓存行为。仅“能跑完”不足以完成负载选型。

## 7. 保存什么，如何判断结果可用

- 保存整个新 run 目录，包括 `state.json`、`launch.json`、`requests.jsonl`、`jobs.json`、`summary.json`、`resources.json`、服务与 helper 日志、调度/传输日志及校验输出；失败时目录不完整也保留。
- 用 `(program, turn)` 核对请求集合，检查缺失、重复、error 和实际输出数量，不只看 summary 的 completed。
- 首次通过标准：`state.status=complete`，16 个程序、178 个唯一预期请求全部完成，实际输出 tokens 等于逐请求计划值，无错误、OOM 或守护中止。
- 比较时保持模型版本、输入文件哈希、等待规则、资源配置、预热与正确性设置一致；每次独立启动，记录运行顺序。
- 正式性能比较使用可核查的独占时段。若不得不使用 `run_relaxed.py`，单列为探索结果，设置唯一 `FOREIGN_LOG`，保持 `RELAX_ABLATION` 未设置；不能仅凭 `resources.json` 的 foreign 字段判断无干扰。
- 缺失指标填“未采集”或“不适用”，不得填 0。客户端总输入 token 数不是 GPU 实际 prefill token 数；历史来源字段不是本次缓存命中率。
