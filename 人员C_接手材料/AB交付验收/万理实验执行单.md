## 2. 第一次上机只验两种方法能否跑通

在个人学号数据盘目录记录实例、GPU UUID/占用、cgroup 限额和当前用量、CPU 允许集合、可用磁盘、模型路径及环境版本。优先找到 B 实际使用的隔离工作区。B 的脚本依赖项目旁的 env 和私有 CUDA 工具链，仅有冻结 Kairos 目录或模型路径还不足以启动。B 交付记录使用 torch/cu130，旧实现交接记录为 cu132，应记录实际组合。

进入 B 的项目目录，按[随包说明](B_运行说明.md)确认 MODEL 指向真实 8B snapshot。下例是针对个人数据盘的命令模板，待现场执行。先检查计划。正式比较优先使用 strict 及协调好的独占时段。

```bash
../env/bin/python scripts/gpu_python.py -m b_replay server-plan \
  --server-profile ram30 --gpu-pid-policy strict \
  --bundle bundles/Qwen3-8B/pilot_1 \
  --arrivals examples/smoke_arrivals/pilot_1_jps0.1_seed20261030.json \
  --model "$MODEL" --method continuum --output runs/c01
```

检查计划中的设备、模型、bundle、arrival 哈希和 CPU 集合。资源满足后用相同参数运行 server-run，再以 kairos 和新目录 runs/k01 重复。两次分别要求 1 程序、10 次唯一请求、2,437 个实际输出 tokens、strict_complete=true、无错误或超时。检查资源样本、OOM 计数及外部进程记录。若 strict 因 PID 映射失败，记录原因；仅能用 record-only 且没有其他独占证据时，将结果列为探索性。若进程确实占卡则换时段。B 的 ram30 使用独立低内存启动逻辑，保留容器内存与 OOM 监测。

## 3. 先选压力点，再花时间做重复实验

1. 在 pilot_14、0.1 JPS 上各做一次两方法试跑。每次应完成 14 个程序、161 个请求、24,182 个输出 tokens。pilot_4（4/44）可用于从单程序过渡或定位失败。14 是整个包的程序数，实际同时活跃的数量由到达时间和服务时间决定。
2. 固定 pilot_14，仅改变首轮到达率。例如把 0.05、0.1、0.2 JPS 作为探索起点。每换一个 JPS 生成对应 arrival 表，保持同一 seed、程序内容和工具等待。先从每种方法一次开始，保留所有失败。
3. 比较实际到达滞后、未完成程序随时间的变化、TTFT/P95、回放结束后的排空和两层内存占用。记录吞吐观察窗。若三点均缺少竞争，逐步提高压力；出现 OOM、超时或无法排空时保留日志，返回较低压力。有限批次只能说明该批次能否跑完。
4. 选定一个可完整运行且能观察到竞争的工作点，交错顺序做每方法至少 3 次独立运行。例：C/K、K/C、C/K（C=Continuum）。开发期调参结束后锁定配置，同样条件在 heldout_candidates（36 程序、401 请求、58,588 输出 tokens）上验证；为该包新建 arrival 表，保留既有开发/留出边界。

## 4. 每轮收什么、最终怎么交
