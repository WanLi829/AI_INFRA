# H800 单卡首轮实验记录

2026 年 11 月 16 日在南京 H800-node82 上运行，11 月 17 日取回 Continuum 日志并与原生 vLLM 的逐请求记录一起复核。

## 结果

在单张 H800 80 GB、Qwen3-8B BF16、每秒 0.1 个新程序的条件下，原生 vLLM 和 Continuum 均完成了全部 14 个多轮程序、161 次模型调用。Continuum 将平均程序完成时间从 25.82 秒缩短至 18.64 秒，下降 27.8%。按原生耗时除以 Continuum 耗时计算，本轮观测加速比为 **1.39 倍**，低于组内提出的 1.5 倍参考目标。回放窗口内的输出吞吐基本持平。

| 单次回放指标 | 原生 vLLM | Continuum |
|---|---:|---:|
| 完成程序 / 计划程序 | 14 / 14 | 14 / 14 |
| 完成调用 / 计划调用 | 161 / 161 | 161 / 161 |
| 输出 token 总数 | 24,182 | 24,182 |
| 程序平均完成时间（含排队及工具等待） | 25.82 秒 | 18.64 秒 |
| 程序完成时间 P95 | 54.34 秒 | 28.61 秒 |
| 请求首 token 延迟 P95 | 145.86 毫秒 | 144.58 毫秒 |
| 从首个程序实际到达到回放结束的窗口 | 140.75 秒 | 141.05 秒 |
| 回放窗口内的输出吞吐（token/秒） | 171.80 | 171.44 |
| GPU KV 缓存容量（token） | 403,872 | 403,872 |
| 回放期间的抢占次数 | 0 | 0 |

两组回放使用同一张到达时间表。总输出量相同，整体回放窗口相差约 0.30 秒，因此平均程序更早完成与整体输出吞吐持平可以同时出现。P95 来自 14 个程序，对个别程序的耗时较敏感。

## 实验条件与证据边界

模型版本为 `b968826d9c46dd6066d109eabc6255188de91218`，五个权重分片及配套文件均通过冻结清单的哈希核验。两种方法使用 vLLM 0.28.0、同一份 `pilot_14` 输入及相同的多轮依赖和工具等待，上下文上限为 16,384 token，并发序列上限为 8。各自从新服务进程开始回放。Continuum 使用 Kairos 提交 `7971fa4`。

平台标示为独享卡。宿主机与容器的 GPU 进程编号无法匹配，故两组按 `record-only` 记录，校验标志 `formal_speedup_eligible` 为假。每种方法仅运行一次，当前结论限于 H800 上这一档低压力试跑。两组均无抢占，且引擎前缀缓存命中和查询计数的增量相同，现有数据不能将耗时改善归因于减少抢占或提高前缀命中率。

本轮已验证两种方法的完整回放流程。建议先在一个更高到达率下重复配对试跑，核实 GPU 进程归属，再加入 vLLM + LMCache、Static TTL 两条基线，逐步扩展到多个到达率。4090/24 GB 的负载选型仍需在目标卡上实测。
