# 任务三：H800 上的并行 Program 规模实验

> 本文可单独转发给本任务负责人。版本：2026-11-18。
> 分工约定：总负责人交付公共代码、固定活跃数回放能力、数据与日志工具；你负责验收该协议、执行规模扫描、核验真实并发并解释结果。最终 PPT 由总负责人汇总。
> 固定活跃数功能和新增方法入口必须通过验收后才能用于正式实验；本文不表示旧脚本已经支持这些能力。

## 1. 你的研究问题

当同时在途的多轮 Agent Program 增多时，vLLM+LMCache、Continuum 各 TTL 配置、Kairos 的性能和资源行为怎样变化？

需要回答：

1. 平均/P95 JCT、TTFT 随活跃 Program 数如何变化？
2. Continuum 是否出现相对基线的收益缩小、反转，或更早出现失败/积压？
3. 增加的程序主要在排队、执行还是等待工具？
4. pin 占用、缓存驱逐、重算、回载和准入等待是否提供机制解释？
5. Kairos 是否缓解问题，有没有性能或公平性代价？

不预设必须观察到退化。所有方法因负载增大而变慢不等于 Continuum 特有缺陷；必须区分绝对延迟增加、相对收益下降和失败率上升。

## 2. 先分清三个数量

| 名称 | 定义 | 本任务如何使用 |
|---|---|---|
| 总 Program 数 N | 一轮回放总共包含的程序实例数 | 控制样本量和测量长度，不等于并行数 |
| 活跃 Program 数 K | 已到达且尚未结束的程序，包含排队、推理、工具等待 | 本任务主动改变的变量 |
| 引擎并发槽位 S | 引擎同时允许执行的请求/序列上限 | 所有 K 档位保持固定 |

例如，K=64、S=8 时，可以有 64 个程序在途，但不意味着 64 个请求同时在 GPU 上运行。程序等待工具时仍计入 K，其历史 KV 是否保留由方法决定。

同一 JPS 下，较快的方法会自然产生较少在途程序。因此本任务采用固定活跃数的封闭负载协议，与另一成员的开放 JPS 实验分开。不能同时声称固定 K 和固定外部 JPS。

## 4. 五种比较配置与验收

| 配置 | 需要确认 |
|---|---|
| vLLM+LMCache | connector 实际启用，CPU KV 预算一致 |

## 5. 固定活跃数回放协议

### 5.1 主实验采用有限工作量、按完成补入

正式前由总负责人将下列协议落实到回放器并提供小样本：

1. 每轮提前冻结包含 N 个实例的待执行列表与顺序，N 应明显大于最大 K。
2. 在测量开始时提交前 K 个 Program，保存每个真实提交/到达时刻；初始化提交的短暂抖动如实记录。
3. 每个 Program 内按原轨迹依赖执行：本轮完成，等待冻结工具间隔，再提交下一轮。不能为了维持 K 把工具等待删掉。
4. 一个 Program 完整结束后，立即按列表顺序补入下一个 Program。补入延迟记录下来。
5. 只要候选列表尚有余量，应维持约 K 个活跃程序；列表耗尽后自然排空，不再声称仍维持 K。
6. 所有计划实例完成后结束本轮；若失败、超时，则按统一失败规则结束或继续收集，结果不得标完整成功。

主结果采用整轮固定工作量统计，所有方法和 K 档尽量使用相同 N、同列表和相同每实例工作量。方法之间完成速度不同，后续实际到达时间必然不同，这是封闭负载的正常结果，不能强行套用 JPS 实验“完全相同的到达表”要求。

Program 的 JCT 从它被补入系统的真实时刻算起；在待执行列表中尚未激活的时间不计入单程序 JCT。整轮完成时间另行报告，反映执行同一批 N 个实例的总时间。

### 5.2 测量窗口与瞬态

- **全程窗口：** 首个 Program 实际到达到最后完成。主 JCT 与完成率覆盖全部已计划实例。
- **目标活跃区间：** 初始 K 个均已提交到最后一个候选实例被补入的区间；报告长度、平均 K(t)、目标达到比例和补入延迟。
- **排空区间：** 候选列表耗尽后至最后完成。其活跃数下降属于预期现象，不当作回放器错误。

目标活跃区间不自动等于稳态。若队列/缓存还在明显变化，不能称稳定运行。不要只挑“同时在窗口内到达并完成”的快程序算 JCT，会遗漏长尾；主 JCT 使用整轮完整样本。

如果公共平台采用持续循环会话或固定时间窗口协议，应在正式前重新登记采样、warmup、停止接纳、排空与未完成任务处理规则，并与本有限列表协议分开报告。不能运行中混用。

### 5.3 失败规则

单个 Program 失败不能当成成功完成来补入新任务并隐瞒。正式主比较要求完整成功；失败轮仍保存全量状态、失败时 K(t) 和后续行为。回放器是否继续补入以采集稳定性信息由总负责人提前冻结，失败轮不进入“完整工作量 JCT 加速”结论。

## 6. 实验矩阵和数据规模

| 项目 | 建议方案 |
|---|---|
| K 候选 | 8、16、32、50、64、80 |
| 五种配置 | 每个正式 K 档全部覆盖 |
| 重复 | 每格至少 3 次配对重复 |
| 全矩阵量级 | 6×5×3＝90 轮，不含小样本、失败和补测 |
| 初期优先级 | 先验通 K=8，再覆盖 16/32 和高档；时间有限先冻结低/中/高代表档 |
| 其他条件 | 使用一套主数据包；S、GPU/CPU KV 等资源固定 |

50、64、80 用于覆盖此前讨论的 50–80 活跃规模；是否全部正式运行取决于数据和先导成本。范围调整提前记录，不能只选 Kairos 好看的点。

N 建议先按至少 `5×最大 K` 估算输入需求，例如 Kmax=80 时准备约 400 个实例，再用先导检查目标活跃区间是否足够长。这是准备启发值，不是保证稳态或统计充分的定理。程序长尾可能需要更大 N；最终 N 和目标区间时长依据先导冻结。

历史 14 个开发程序或 36 个留出程序单独无法支撑 K=80。不能将 N=80、一次性全发的实验写成“持续维持 80 并发”，那主要是突发后排空。

### 独立数据不足时

优先扩充未参与训练的真实轨迹。若允许同一轨迹复制为多个独立会话实例：

- 为每个实例设置唯一 ID，保留源任务/轨迹 ID。
- 固定实例列表和排列，避免连续大量同源副本形成特殊热缓存。
- 保留同一实例跨轮前缀复用；按公共协议防止不同复制实例意外共享整条历史 KV，或明确报告共享策略及影响。
- 不修改文本来偷偷打散缓存，也不删除自然共享前缀；采用哪种隔离策略必须由公共工具一致实施。
- 报告“独立源轨迹数”和“运行实例数”，不把 400 实例称为 400 条独立真实轨迹。
- 检查与当前预测器训练身份的重叠；来源不足时说明泛化限制。

跨重复可以改变实例顺序，但同一重复号的所有方法、所有 K 使用相同冻结列表/顺序。记录种子与哈希；若统一平台采用不同配对规则，需说明。

## 8. 执行步骤

1. **小规模验收协议。** 用 K=2 或 4、N>K 的小样本检查初始接纳、工具等待、结束补入、列表耗尽和排空；逐事件重算活跃数。
2. **验通五配置。** 确认完成量、输出 token、策略实际启用；不能只看进程启动成功。
3. **先导定规模。** 从 K=8 向上增加，检查目标区间、补入速度、内存、队列和超时；冻结正式 N、K、资源和超时。
4. **配对运行。** 每档每重复轮换五种方法的执行顺序，各轮从新服务和统一缓存状态开始。按共享排期串行上卡。
5. **逐轮验收。** 核对 N 个实例、调用数、输出 token、依赖/等待、实际 K(t)、失败与策略日志。目标 K 达不到先检查回放器，不直接归因于系统。
6. **先交一套完整配对结果。** 附真实并发曲线，证明横轴设置得到执行。
7. **补齐重复与机制分析。** 对低压和性能转折档检查队列、pin、重算与回载。
8. **交归档和素材。** 保存所有成功/失败轮，下载并核验归档可打开。

同卡不并行运行多个正式服务；只管理自己创建且身份明确的进程。结束后按约定交接或关机并核实状态。预算计入加载、等待、下载；旧材料的预算授权不能继承。

## 9. 实际并发必须从事件复算

对程序 i 的实际到达 a_i 和结束 e_i：

`K(t) = Σ 1[a_i ≤ t < e_i]`

同一时刻完成与补入按该左闭右开区间处理，事件排序一致。未结束程序在观察截止时仍活跃；不能从图中直接删掉。

每轮至少报告：设置 K、观测峰值、全程时间加权平均、目标活跃区间平均、目标达到比例、补入延迟均值/P95、初始填充和排空时长。目标达到比例定义为目标区间内 `K(t)=K目标` 的时间占比；另报告低于和高于目标的时长。阈值要求由先导后冻结，不能看结果后修改。

如果有状态事件，将活跃数分为排队/准入等待、执行、工具等待等互斥状态，定义状态边界，避免一条程序被重复计数。没有状态数据时只画总活跃数并标明限制。

资源曲线尽量使用固定采样频率；活跃数优先由精确事件计算，不能只靠低频 GPU 采样推断。工具期计入活跃，不代表该程序一定占有 GPU KV。

## 10. 性能和机制指标

| 指标 | 口径与用途 |
|---|---|
| 平均/P95 JCT | 每 Program 最后完成−实际激活/外部到达，含排队与工具等待 |
| 平均/P95 TTFT | 每调用首 token−提交，包含请求排队 |
| 完成率 | 已完成/计划实例与调用，另列失败、超时、未提交 |
| 吞吐和整组时间 | 同一 N 的完成吞吐、输出 token/s、全程时间；窗口明确 |
| 队列与准入 | 等待时间、等待长度、容量不足事件，解释是否受阻 |
| pin/KV | 物理唯一 pin 页占预算比例、可用页、实际 KV 占用；不能用整卡显存替代 |
| 驱逐与重算 | 分别记录抢占、页驱逐、重新计算 token/耗时，注明单位 |
| CPU 恢复 | 回载字节/token/耗时，观察容量与传输影响 |
| GPU/CPU 缓存指标 | 分层报告、明确分母和计数窗口；避免重复计入 GPU 与 CPU 命中 |

缺指标填 NA。共享页多引用时，pin 页数按公共工具定义去重；若只能得到引用计数，明确不是物理唯一页。采样到的“GPU 很忙”不能直接证明有用吞吐高。

每轮先计算 Program 等权平均/P95 JCT 和调用级 TTFT，跨轮报告统计量均值与范围。三次重复是三次运行，不是每个请求都算一次独立重复。失败轮和未完成程序单列，不用幸存者 JCT 宣称更快。

相对降低比例按同 K、同 N/列表、同资源的基线计算：`(vLLM+LMCache JCT−方法 JCT)/vLLM+LMCache JCT`。Kairos 对 Dynamic 另外列。若比较平均活跃数与吞吐×平均 JCT，只能在近似稳态且边界一致时作辅助核对，不能用全程排空数据机械套公式。

## 11. 图表与解释要求

至少交付：

1. K—平均/P95 JCT 图，五种配置，重复范围说明。
2. K—平均/P95 TTFT 图。
3. K—完成吞吐、完成率图，失败明确标记。
4. 每档或代表档的 K(t) 曲线，标出填充、目标活跃区间、排空。
5. K—GPU/CPU 缓存指标，以及 pin 占用、排队、驱逐/重算、回载中的可靠指标。
6. 低档与转折/高档的机制对照表，说明实际资源瓶颈。

解释时检查以下可能性，但不把它们预写成结论：

- pin 保留更多，却压缩了新请求执行空间；需要准入等待与可用页证据。
- 频繁抢占/驱逐带来重算；需要计数和时间对照，不只看命中率。
- CPU 回载减少重算却增加传输等待；需要回载量和耗时。
- 工具等待多，活跃程序多但同时 ready 的请求很少；不能把 K 高直接当成 GPU 压力大。
- Kairos 降低平均 JCT，但尾部或部分程序变差；应报告 P95、长等待和逐程序差异。

如果 H800 原始资源下无退化，如实写“在所测范围未观察到”。需要缩小 KV 做压力补充时，所有方法统一变更并另建组，不把人工容量限制当作原始 H800 结论。

## 12. 异常、停止与补测

- K(t) 长时间低于目标：检查列表是否耗尽、补入器是否被请求执行阻塞、客户端连接/并发限制、工具等待是否被误排除。
- K(t) 超过目标：检查结束/补入事件与重复提交；协议错误修复前不能使用该轮作为固定 K 结果。
- OOM、超时、死锁或错误：保存命令、版本、输入、资源和日志；反馈总负责人，按预定规则结束，不能临时调大资源掩盖失败。
- 代码、数据、TTL、资源、超时改变：新建版本，重新跑受影响的配对组。
- 指标缺失：标 NA；主要时间字段或活跃事件缺失时补采，不能凭配置推断实际并发。
- GPU 归属和干扰无法核实：标探索性，不能冒充正式独占结果。
