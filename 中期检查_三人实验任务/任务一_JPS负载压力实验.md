## 1. 你需要回答什么

在相同 H800、模型、数据和资源限制下，随着每秒到达的新 Program 数增加，vLLM+LMCache、Continuum 各 TTL 配置与 Kairos 的性能如何变化？

具体回答：

1. 平均和尾部 JCT、TTFT 随 JPS 怎样变化？
2. Continuum 相对 vLLM+LMCache 的优势是否缩小或反转？发生在哪些实测档位？
3. Zero、Static、Dynamic TTL 的差异，是否随压力变化？
4. 若出现性能恶化，日志更支持排队增长、缓存保护阻碍准入、重算增多，还是其他解释？
5. Kairos 的收益和代价是什么？是否存在无收益或退化的档位？

目标是得到可复核的结果，不是必须证明 Continuum 退化或 Kairos 获胜。正常增长的绝对延迟和相对基线的退化要分开描述。

## 4. 比较配置

本轮“三类系统”展开为五种配置：

| 报告名称 | 定义与验收要求 |
|---|---|
| vLLM+LMCache | 标准基线；确认 connector 启用和 CPU KV 配置 |
| Continuum–Zero TTL | 不额外 pin 保留轮间 KV；其他 Continuum 机制保持一致；不等于关闭所有前缀缓存 |
| Continuum–Static TTL | 预先固定 TTL；若采用 2 秒，标为“固定 TTL 2s 工程对照” |
| Continuum–Dynamic TTL | 本次冻结实现的动态 TTL；记录策略版本、初始化和更新规则 |
| Kairos | 本次冻结的完整方案；核验预测器与策略实际启用 |

原生 vLLM 仅在总负责人安排时作为第六条辅助对照，不替代 vLLM+LMCache。若使用 Continuum 兼容实现，报告应注明，不宣称完整复现作者全部系统。

旧入口只有 `native/lmcache/static_ttl/continuum/kairos`，且 Static TTL 参数要求正数。Zero TTL 的新命令和验收方式必须由总负责人提供；不能把旧入口的 TTL 参数填 0 当作已实现。新版方法名以交付命令为准，本文不编造尚未存在的命令。

## 5. 实验设计：只主动改变 JPS

### 5.1 明确概念

- 一个 Program 是一条多轮 Agent 轨迹；一轮 Program 可以包含一次 LLM 调用及后续工具等待。
- JPS 是每秒新到达的 Program 数，不是 LLM 请求数/秒。
- 本任务采用开放到达：按冻结时间表提交新 Program，不等待前面的 Program 完成。
- 活跃 Program 包含已到达且未完成的排队、推理、工具等待程序，是本任务的观测结果。
- 不通过客户端并发上限偷偷延迟新 Program，以免高 JPS 被限流成低 JPS。若必须有安全上限，提前记录；触发后该轮标为受限，单独解释。

### 5.2 建议矩阵

| 项目 | 建议 |
|---|---|
| 数据 | 一套冻结的主测试包，各档位程序列表与顺序一致 |
| JPS | 初始候选 0.1、0.5、1、2；小规模先导后冻结正式档位 |
| 方法 | 五种配置全部覆盖 |
| 正式重复 | 每个方法×JPS 至少 3 次完整配对重复 |
| 配对方式 | 同一重复号共享程序列表和到达表；不同重复号使用预登记种子 |
| 数量估计 | 4 档×5 配置×3 次＝60 轮，不含验通、失败与补测 |

种子可由总负责人统一指定三枚，例如 2026111801、2026111802、2026111803。泊松到达应保存实际生成的表，不依赖“相同种子”口头保证。若生成器支持，可使用同组随机间隔按 JPS 缩放；采用哪种方式写清楚。

0.1 JPS 下平均到达跨度约为 `(N−1)/0.1` 秒，启动和排空还需额外时间。先估计费用和排期，不能直接提交整个矩阵。若时间不足，先做低/中/高三个代表档的五配置完整对照并补齐重复；减少档位需记录，不能删掉表现不好的结果。

### 5.3 必须固定的条件

同一可比实验组固定 GPU、模型与 tokenizer、代码、预测器、测试轨迹、输出工作量、工具等待、GPU/CPU 缓存预算、引擎槽位、批处理参数、超时、冷启动和采样规则。CPU 亲和性也应一致。

工具等待从上一轮真实完成后开始计时；后续请求不能在依赖完成前提交。固定回放可以由驱动器知道目标输出长度，但调度器/预测器只能看到部署协议允许的历史信息，不能偷看未来标签。

H800 80GB 下可能长期没有缓存压力。先检查实际 KV 容量、队列和在途规模，再决定是否补更高 JPS 或更大输入。若另做缩小 KV 预算的压力实验，所有方法统一缩小，标为独立补充组，不能混入原资源主结果。

## 6. 执行步骤

1. **冻结方案。** 写下矩阵、版本、预算、超时、种子、方法顺序和测量窗口。
2. **验通。** 用总负责人提供的小样本逐方法运行，确认策略生效、依赖顺序和结果汇总均正确。
3. **先导。** 从低压力逐档增加，核验到达精度和是否出现排队。先导数据单列；若据此修改配置，不能与修改后结果直接合并。
4. **正式运行。** 同一 JPS 内按重复号配对运行五种配置。使用预登记的轮换顺序，避免永远某方法第一、某方法最后。每轮启动全新服务，按统一协议处理缓存；初始化完成后再计回放时间。
5. **逐轮验收。** 对照计划完成数、调用数和输出 token；检查实际到达偏差、CPU/GPU 干扰、超时、OOM 和方法日志。验收不通过先保留现场并反馈。
6. **生成中间结果。** 第一套完整配对结果出来即交总负责人，不等全部完成；标清只有一次，不下稳定结论。
7. **补齐重复和必要转折点。** 新档位只用于补充已发现的问题，记录加入原因，不按方法优劣挑选档位。
8. **汇总、分析和归档。** 从原始记录重算表格，输出图表和报告，下载日志并验证压缩包可打开。

同一张 GPU 上正式运行串行执行；不要并行启动多个服务。只停止自己创建且身份明确的进程。共享实例结束后按约定交接或关机，并核实状态；历史文档里的费用授权不适用于本轮。

## 7. 统一指标与计算口径

| 指标 | 定义 |
|---|---|
| Program JCT | 最后一轮完成时间减实际外部到达时间，包含排队、推理和工具等待；不能从引擎开始执行算起 |
| TTFT | 每次请求提交到首 token 的时间，包含该请求排队；记录 mean 和 P95，单位统一为秒 |
| 完成率 | 完成 Program/计划 Program，并列调用完成率、失败、未提交和超时数 |
| 活跃数 | 对区间 `[actual_arrival, end)` 计数；报告峰值和全测量窗时间加权均值 |
| 完成吞吐 | 测量窗口内完成 Program 数/窗口秒数 |
| 输出吞吐 | 同一窗口内实际输出 token/窗口秒数 |
| 整组时间 | 第一个 Program 实际到达到最后完成；含到达过程与排空，不等同于 GPU 饱和吞吐 |

每轮先按 Program 计算平均/P95 JCT，按调用计算平均/P95 TTFT；跨轮报告各轮统计量的均值和范围，注明重复数。P95 使用统一工具固定的算法，不把每次调用当成独立实验重复。三次重复不自动构成统计显著性。

缓存指标由总负责人冻结字典：若能够得到同一 token 口径，分别报告 GPU 直接复用量和 CPU 补充恢复量占输入 token 的比例，避免重复计数。若只能取得引擎的 hit/query 指标，则保留其实际定义，不与其他系统不同分母的比率混画。报告测量前后 counter 增量；分母为零或缺失时填 null/NA，不填 0。

主要相对指标：

- 相对 vLLM+LMCache 的 JCT 降低比例＝`(基线平均 JCT−方法平均 JCT)/基线平均 JCT`。
- Kairos 相对 Dynamic 的 JCT 降低比例，使用同样公式，明确分母。
- 加速比＝`基线平均 JCT/方法平均 JCT`，不能与百分比混写。

相对结果只在同档位、同输入、同资源、同完成口径的配对结果间计算。失败轮不能从总体中悄悄删除；部分完成 JCT 只作描述，不用它宣称总体加速。

## 8. 怎样解释结果

至少输出以下图表：

1. JPS—平均 JCT 折线图，五种配置，误差范围标明是重复范围。
2. JPS—P95 JCT、平均/P95 TTFT 图，可分面显示。
3. JPS—缓存指标图，GPU/CPU 口径分开。
4. JPS—实际活跃数、完成率或队列长度辅助图。
5. 一个代表低压档和一个转折/高压档的机制对照：pin 占用、等待时间、抢占/驱逐、重算和回载，选有可靠日志的项目。

解释顺序是“观测到什么→哪些日志支持→还有什么替代解释”。例如，只有 pin 较高不能证明阻碍准入；还需可用页不足、准入受阻、队列等待，以及 TTL 对照的共同证据。抢占次数、缓存页驱逐次数和重算 token 是不同量，不可互相替代。

不要把 JCT 改善直接写成 token 吞吐提升。低 JPS 下整组时间可能由到达表决定，各方法输出吞吐接近仍可同时存在 JCT 差异。若所有方法都排队增长，要看 Continuum 相对基线的变化，而非仅看其绝对延迟增加。

## 9. 失败和变更处理

- 日志缺字段：标 NA，反馈补采；关键指标缺失则该轮不能进入对应正式图表。
- 请求失败、OOM、超时：保留完整目录和错误，记录计划/完成/失败数；不自动跳过失败程序重算“完整结果”。
- 发生稳定积压：报告窗口、队列趋势和未完成数；到预定超时后按协议结束，不能无限等待或临时改超时。
- 发现代码错误：提供最小输入、命令、版本、日志和预期/实际行为给总负责人。修复后重跑受影响的配对组。
- 调整 TTL、缓存、模型、数据或预测器：新建实验版本，不能与旧配置拼接成同一曲线。
- GPU 独占/进程归属无法核实：保留证据并标为探索性，不假称正式隔离运行。
