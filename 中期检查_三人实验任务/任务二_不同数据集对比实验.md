# 任务二：H800 上的不同数据集对比实验

> 本文可单独转发给本任务负责人。版本：2026-11-18。
> 分工约定：总负责人提供统一可运行平台、数据转换与回放接口、指标和日志工具；你负责数据验收、特征分析、跨数据集实验及解释。最终 PPT 由总负责人汇总。
> 本文建议的档位和样本规模须在先导后冻结；没有验收的数据包不视为已经具备正式实验条件。

## 1. 任务目标

回答：不同 Agent 轨迹的数据特征，会怎样影响 vLLM+LMCache、Continuum 各 TTL 配置和 Kairos 的端到端表现？

具体问题：

1. 两套数据在轮数、输入/输出长度、工具返回间隔和前缀复用上有什么不同？
2. 相同硬件与到达率下，各方法在每套数据上的平均/P95 JCT、TTFT 和缓存效果怎样？
3. Continuum 在哪类轨迹上相对收益更大或更小？Kairos 是否保持收益？
4. 差异可能来自更高计算需求、工具等待、缓存规模、调度竞争，还是多种因素共同变化？
5. 当前证据能支持多大范围的结论？

不能把“数据集 A 的 JCT 高于 B”直接当成方法退化。应先看同一数据集内各方法的相对表现，再比较相对收益随数据集的变化。

## 4. 数据验收：每个数据集都做

### 4.1 结构和时间

- 每个 Program 和每次调用有稳定唯一 ID，轮次连续，依赖关系可重建。
- 模型输入有实际消息或可恢复的 token 内容，不是只有哈希。
- 每轮输出工作量有可靠记录；输出长度按本轮统一 tokenizer/协议定义。
- 工具返回间隔来源明确，逐项排除缺失、负值和异常时序。
- “最后工具反馈时间−回答完成时间”包含环境和客户端开销时，称为工具返回间隔，不能称为纯工具 CPU 时间。
- 多个工具并行/连续返回时，以冻结转换规则确定下一轮 ready 时间，不能随意把所有间隔相加。
- 缺失间隔不能默认填 0。优先使用有效轨迹；若只能采用补值或合成等待，提前登记为独立的敏感性实验。

### 4.2 结束状态和长度

- 区分自然结束、达到 step/token/time limit、失败和截断。
- 自然结束轨迹优先用于主实验；若回放受限结束轨迹，标为“记录轨迹完成时间”，不当作自然任务完成时间。
- 按统一上下文上限检查每轮输入及输出空间。超长处理由总负责人统一确定：过滤或采用明确的公共规则。
- 禁止静默截断长 prompt 或删轮；这会改变前缀复用、工作量和结论。
- 记录过滤前后 Program 数、调用数和每种排除原因，以及样本分布改变。

### 4.3 训练泄漏和重复

- 按源任务/轨迹身份核对训练、验证、测试，不只比较文件名。来自同一任务的多个轨迹也要识别。
- 正式泛化结果优先使用独立留出的源任务；开发集和已参与调参的数据单列。
- 无法核实切分时标“训练重叠未知”，不能宣称独立测试泛化。
- 重复轨迹生成多个实例时保留 `source_id` 和 `instance_id`，不能把实例数写成独立样本数；统一检查跨实例缓存隔离。

### 4.4 必交数据表

`dataset_manifest.csv` 至少包含：dataset_id、source_revision、source_task_id、source_trajectory_id、instance_id、split、终止类型、轮数、输入/输出 token 汇总、总工具等待、时间校验状态、纳入/排除原因、数据包哈希。

原始数据审计表与运行测试表分开保存；过滤规则写在 `data_audit.md`，不能只交最终剩余样本。

## 5. 特征统计：实验前先交一版

| 特征 | 统计粒度与内容 | 解释用途 |
|---|---|---|
| Program 轮数 | 每程序，均值/P50/P90/P95和分布 | 长程序及多次复用机会 |
| 输入长度 | 每调用，均值/P50/P90/P95和最大值 | 上下文规模、prefill和 KV 压力 |
| 输出长度 | 每调用，同上；另统计每程序总输出 | decode 工作量 |
| 工具返回间隔 | 每有效间隔，分位数；每程序总等待 | 空闲保留成本与 TTL 适配 |
| 前缀复用机会 | 统一渲染和分词后，相邻轮可复用历史的比例 | 潜在缓存收益；不等于实测命中率 |
| 上下文增长 | 每轮长度变化、末轮长度、长尾比例 | 工作集扩大趋势 |
| 工具/动作类别 | 分类规则、各类占比及间隔分布 | 动态 TTL 经验是否适配 |
| 质量与规模 | 独立程序数、实例数、调用数、过滤比例、终止状态 | 结论覆盖范围 |

前缀统计应按实际回放的 prompt/token 序列计算，明确是否包含上一轮 assistant 输出；不能仅比较字符串字符前缀。特征表使用 H800 回放模型的统一 tokenizer。整体调用统计会偏重长 Program，因此关键特征同时给出 Program 粒度汇总，并标注权重。

## 6. 五种配置与共同条件

五种配置为 vLLM+LMCache、Continuum–Zero TTL、Continuum–Static TTL、Continuum–Dynamic TTL、Kairos。原生 vLLM 可作辅助，但不替代主基线。

Zero TTL 是不额外保留轮间 pin，不代表禁用普通前缀缓存。Static 若用固定 2 秒应称工程对照；Dynamic 的初始化历史及在线更新规则要冻结。Continuum 各 TTL 组保持其余机制一致。若为仓库兼容实现，在报告中标明。

同一方法跨数据集使用同一预测模型和同一套预登记配置，不在每个测试集上单独调参后选最好结果。工具经验分布可以按统一在线算法更新，但初始化、更新顺序及允许信息必须相同且可追踪；不能预先读完整测试集未来间隔。

同组固定：H800 与 GPU UUID、模型/revision/精度/tokenizer、上下文上限、GPU/CPU KV 预算、引擎槽位与批处理参数、CPU 资源、代码和预测器、采样规则、超时、缓存初始化。数据集不同是本任务主动变化项，实际调用数、token 和等待量应如实报告。

## 7. 实验矩阵与公平性

### 7.1 主实验

建议两套数据、两档公共 JPS、五种配置、每格三次完整重复，共 `2×2×5×3＝60` 轮，不含先导和补测。两档建议从 JPS 实验结果中选择低压力与较高压力的代表档，正式运行前冻结；不是为每个方法分别选择最优 JPS。

- 优先从两个测试集中按预登记种子抽取相同数量的独立 Program，数量由可用独立测试样本和运行预算决定。
- 同一数据集内，各方法使用完全相同的 Program、顺序、到达表、输出工作量和工具间隔。
- 两数据集程序数相同时，同一重复号可以复用到达时间戳，轨迹身份不同；不人为匹配到只剩相似样本而不报告。
- 若只能使用不同程序数，明确说明到达跨度和尾部排空差异；相对收益在各自数据集内计算，不直接比较 makespan 大小。
- 每个重复号的种子、样本列表和到达表保存到文件。若不同重复仅改变到达表而不换轨迹，报告中说明没有覆盖抽样不确定性。

### 7.2 不同数据不等于单一特征因果实验

同一 JPS 下，长程序数据集每秒带来的计算工作可能更大。必须报告每程序平均调用数、输入/输出量和等待，并结合实际队列/KV 压力解释。

主实验是现实数据分布的整体对比。若要强调“工具等待导致差异”等单一机制，需要另做控制其他条件的分组或敏感性实验。可选补充：在同一数据源按预先确定的长度/等待阈值分层；或者使用独立标定的服务需求匹配负载。不能用实测各方法 JCT 分别调到不同 JPS 后仍称同到达率比较。

### 7.3 第二套数据尚未就绪怎么办

先提交明确缺项和可用部分，继续完成第一套数据的特征分析和基线。经总负责人调整范围后，可做同源长/短上下文或长/短等待分组，标题写“数据特征分组实验”；不得改名为跨数据集结果，也不伪造缺失的真实工具时间。

## 8. 运行步骤

1. 向总负责人验收冻结环境、五种方法、数据包、命令、日志字典和预算；将信息写入 `experiment_spec.md`。
2. 两套数据分别选择小样本，用全部配置验证消息、依赖、输出 token、工具间隔和结束状态。
3. 提交数据审计和特征表，确定正式样本与公共 JPS；小样本失败先修接口，不直接扩大规模。
4. 在每个“数据集×JPS×重复号”内配对运行五种配置。轮换方法顺序，各轮从新服务和统一缓存状态开始。
5. 每轮结束核对完成数、调用数、输出 token、到达偏差、策略日志和资源状态；立即保存失败记录。
6. 第一套完整配对数据尽早交总负责人，与 JPS 成员核对同条件结果是否一致。
7. 完成重复，生成图表，选择代表性差异检查机制日志。
8. 交付归档、报告和 PPT 素材；下载并检查文件完整性。

旧入口不完整覆盖 Zero TTL，新命令由总负责人提供；不要猜参数名或把 Static 填 0。旧 GPU 结果、旧森林预测器与新 MiniLM 版本结果不混用。

同一 H800 上正式服务串行运行；与另外两人共享排期。估计总时长时计入模型加载、回放、工具等待、日志下载。结束时按约定交接或关机，核实状态；不继承历史费用授权。

## 9. 指标与结果表

- JCT＝最后一轮完成−Program 实际外部到达，含排队与工具等待。
- TTFT＝每次请求首 token−请求提交时间；报告每轮 mean/P95，统一秒。
- 每轮先计算 Program 等权平均/P95 JCT；调用口径计算 TTFT。跨轮汇总各轮统计量的均值和范围，注明重复数和样本数。
- 命中率使用公共指标字典，GPU 直接复用与 CPU 补充恢复分别报告，注明分母和 counter 增量；取不到填 NA，不用不同口径做横向排名。
- 同时记录完成率、失败/超时、总调用/token、活跃 Program、队列、pin 占用、抢占/驱逐、重算、回载和吞吐。不同数据规模下可另给每调用/每千输入 token 的事件率，但保留原始计数和分母。
- JCT 含真实等待。可补充“JCT−按协议实际执行的工具等待”，明确这是剩余时间，仍包含排队和客户端开销，不称纯 GPU 服务时间。
- 相对收益按同数据集、同 JPS 的配对基线计算：`(vLLM+LMCache JCT−方法 JCT)/vLLM+LMCache JCT`；Kairos 对 Dynamic 的收益另外列。
- 不把完整失败轮剔除后宣称整体更优；部分完成统计单列。少于三次标探索性，不因为调用很多就宣称统计显著。

## 10. 图表、解释与 PPT 素材

至少交付：

1. 数据特征对照表，包含过滤后的实际测试规模及训练重叠状态。
2. 轮数、上下文长度和工具间隔的分布图，选能说明差异的 2–3 张。
3. 按数据集/JPS 分组的平均/P95 JCT、TTFT 对比图。
4. 各数据集内相对 vLLM+LMCache 的收益图，避免只看原始耗时。
5. GPU/CPU 缓存指标及代表性的排队、pin、重算/回载对照。

每张图提供 PNG、SVG 或 PDF、底表和生成命令，标单位、方法、样本数、重复数、误差条含义。无数据留缺失标识，不能画成零柱。

分析按“数据特征→可能影响的机制→实测结果→支持证据→局限”组织。例如，长上下文意味着更多可复用历史，但也占用更多 KV；究竟收益扩大还是竞争更重，必须看本次实测。没有控制变量时用“与……一致/可能相关”，不写成已证明单一因果关系。

PPT 素材交 1–2 页：数据差异一页、对比与解释一页；每页含标题、主图、3 条结论、配置脚注、约 1 分钟讲稿。最终排版由总负责人完成。

## 11. 异常与变更

| 情况 | 处理 |
|---|---|
| 数据缺正文、输出或时间 | 提交缺项；不静默补零或随意合成 |
| 无法核验训练身份 | 标记未知；不宣称独立泛化 |
| 超上下文、截断、受限结束 | 按冻结规则过滤/分组并留记录，不运行中临时改长度 |
| 某方法失败/OOM/超时 | 保留全部日志、完成情况和错误；不能只报告幸存样本 |
| 公共代码或统计错误 | 反馈最小复现；修复后重跑受影响对照或统一重算 |
| 版本/资源/TTL 改变 | 新建实验组，说明原因，不能并入旧组 |
| 指标缺失或 GPU 干扰 | 标为不可用/探索性，安排补测，不伪造正式核验 |

不要为让不同方法完成而各自使用不同超时、上下文或缓存。必要变更必须统一，并重新建立配对关系。
